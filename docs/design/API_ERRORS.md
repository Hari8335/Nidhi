# Nidhi v1 Standard API Error Model

This document defines the error handling protocol, HTTP status code semantics, RFC 7807/9457 Problem Details response envelope, and stable application error codes for Nidhi v1. It implements the requirements in [OPEN_DECISIONS.md](../requirements/OPEN_DECISIONS.md) and [NON_FUNCTIONAL_REQUIREMENTS.md](../requirements/NON_FUNCTIONAL_REQUIREMENTS.md) (NFR-SEC-004).

---

## 1. Error Response Envelope: RFC 7807 / RFC 9457 Problem Details

All error responses from the Nidhi ASP.NET Core API return `Content-Type: application/problem+json`.

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "The submitted price version '018f3a5b-...' is no longer current. The latest price is LKR 31,500.0000 per gram.",
  "instance": "/api/v1/customer/gold-purchases",
  "code": "PRICE_CHANGED",
  "timestampUtc": "2026-09-24T08:15:00.123Z",
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "errors": {}
}
```

### Fields Specification
- `type`: `about:blank`, the registered HTTP-status problem type. No owned production error-document origin is approved. Application-specific handling uses the stable `code` extension; no fabricated hostname or relative endpoint-dependent type is emitted.
- `title`: Standard HTTP status phrase (for example, `Conflict` for 409). The occurrence-specific explanation remains in `detail`. See [RFC 9457 section 4.2.1](https://www.rfc-editor.org/rfc/rfc9457.html#section-4.2.1).
- `status`: The HTTP status code generated by the origin server.
- `detail`: Human-readable explanation specific to this occurrence of the problem. Must **never** leak database stack traces, SQL syntax, or internal credentials (NFR-SEC-004).
- `instance`: The URI reference of the endpoint that originated the error.
- `code`: Stable, enumerated machine-readable application error code.
- `timestampUtc`: UTC timestamp when the error occurred.
- `traceId`: Current Activity identifier (W3C format when available), otherwise the HTTP request trace identifier, for log correlation and operational troubleshooting (NFR-OBS-001).
- `errors`: Optional dictionary of field-level validation errors (used exclusively with `VALIDATION_ERROR`).

## 2. Stable Application Error Codes

To eliminate ambiguity across client implementations and automated testing, Nidhi defines a curated set of stable error codes.

### 2.1. Authentication & Authorization Errors

| HTTP Status | Application Error Code | Meaning / Trigger Scenario |
|---|---|---|
| `401 Unauthorized` | `AUTHENTICATION_REQUIRED` | Request requires an authenticated session cookie, but no valid session was provided. |
| `401 Unauthorized` | `INVALID_CREDENTIALS` | Login attempt failed due to invalid email/password, account lockout, or an unsupported role set. Does not disclose whether email exists. |
| `403 Forbidden` | `FORBIDDEN` | Authenticated caller does not have permission (e.g., Customer invoking an Admin endpoint). |
| `403 Forbidden` | `EMAIL_NOT_VERIFIED` | Customer has registered but has not yet verified their email. Simulated financial features are blocked until verification (OD-002). |

---

### 2.2. Validation & Resource Errors

| HTTP Status | Application Error Code | Meaning / Trigger Scenario |
|---|---|---|
| `400 Bad Request` | `VALIDATION_ERROR` | Request body or parameters failed syntax/range/format rules. Optional `errors` field contains safe field-level messages when available. |
| `400 Bad Request` | `INVALID_TOKEN` | Password reset or email verification token is invalid, expired, wrong-account, or already used. Missing/oversized token fields instead fail request validation with `VALIDATION_ERROR`. |
| `404 Not Found` | `RESOURCE_NOT_FOUND` | Requested entity (e.g., customer, transaction) does not exist or caller does not own it. |
| `409 Conflict` | `EMAIL_ALREADY_EXISTS` | Registration attempt with an email that is already registered. |
| `409 Conflict` | `ACTIVE_GOAL_ALREADY_EXISTS`| Attempt to create an active goal when one already exists, including concurrent creation; replacement is not supported in v1. |

---

### Session 5 infrastructure errors

| HTTP Status | Application Error Code | Meaning / Trigger Scenario |
|---|---|---|
| `400 Bad Request` | `CSRF_VALIDATION_FAILED` | Missing/invalid antiforgery header/cookie pair; fetch a fresh token. |
| `405 Method Not Allowed` | `METHOD_NOT_ALLOWED` | Route exists but does not support the requested HTTP method. |
| `415 Unsupported Media Type` | `UNSUPPORTED_MEDIA_TYPE` | Request body must use a supported JSON content type. |
| `429 Too Many Requests` | `RATE_LIMITED` | Auth request limit exceeded; respect `Retry-After`. |
| `503 Service Unavailable` | `IDENTITY_EMAIL_UNAVAILABLE` | Registration email delivery unavailable; registration rolls back and can be retried. Password recovery still returns its generic response. |
| `500 Internal Server Error` | `INTERNAL_ERROR` | Unexpected failure with no framework exception or sensitive details in the response. |

Session 5 uses the four authentication/authorization codes above, `VALIDATION_ERROR`, `INVALID_TOKEN`, `EMAIL_ALREADY_EXISTS`, and the six infrastructure codes in this table. Framework routing also uses `RESOURCE_NOT_FOUND`. Financial/design codes elsewhere in this catalog are not implemented authentication errors. Clients must branch on `code` and HTTP status, not human-readable `title`/`detail`; Session 13 uses the HTTP status phrase for title and the safe application explanation for detail.

Verification and password reset both retain `INVALID_TOKEN` for invalid, expired, wrong-account, or reused tokens.

### 2.3. Financial & Simulation Errors

| HTTP Status | Application Error Code | Meaning / Trigger Scenario |
|---|---|---|
| `422 Unprocessable` | `INSUFFICIENT_SIMULATED_FUNDS` | Gold purchase amount exceeds customer's available wallet balance (`amountLkr > wallet.BalanceLkr`). |
| `422 Unprocessable` | `WALLET_LIMIT_EXCEEDED` | Funding operation would cause wallet balance to exceed LKR 5,000,000.00 (OD-003). |
| `422 Unprocessable` | `DAILY_FUNDING_LIMIT_EXCEEDED` | Customer has already completed 20 successful funding operations in the current UTC calendar day (OD-003). |
| `422 Unprocessable` | `GOLD_AMOUNT_OUT_OF_RANGE` | Gold purchase amount is `< 100.00` or `> 1,000,000.00` LKR, or has more than 2 decimal places (OD-004). |
| `422 Unprocessable` | `GOLD_QUANTITY_ZERO` | After rounding down to 8 decimal places, the calculated gold grams are `0.00000000` (OD-005). |

---

### 2.4. Price Freshness & Publication Errors

A critical architectural distinction is made between the three price error states (OD-006, OD-017):

| HTTP Status | Application Error Code | Semantic Distinction |
|---|---|---|
| `409 Conflict` | **`PRICE_CHANGED`** | **The customer submitted a valid, previously active price version, but a newer price version was published before execution.** Rejection requires the customer to review the new price and reconfirm. Silent substitution of the new price is strictly prohibited. |
| `503 Service Unavailable` | **`PRICE_STALE`** | **The active price version exists, but its publication timestamp is older than 24 hours.** The pricing service is temporarily unavailable for executing purchases until an Administrator publishes an updated price. |
| `503 Service Unavailable` | **`PRICE_UNAVAILABLE`** | **No usable published price version currently exists in the system.** Occurs in production before an Administrator publishes the very first price version (OD-017). Purchases and quotes are unavailable. |

---

### 2.5. Idempotency & Concurrency Errors

| HTTP Status | Application Error Code | Meaning / Trigger Scenario |
|---|---|---|
| `409 Conflict` | `IDEMPOTENCY_CONFLICT` | The supplied `Idempotency-Key` was previously used for this operation with a **different request payload** (OD-012). |
| `409 Conflict` | `OPERATION_IN_PROGRESS` | A request with the same `Idempotency-Key` is currently executing concurrently. Client should retry after a short delay. |

## 4. Price Changed Conflict Response Example

When a customer attempts to save gold using a price that has been superseded:

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "The price version submitted (018f3a5b-...) is no longer current. Please reconfirm your purchase with the updated price.",
  "instance": "/api/v1/customer/gold-purchases",
  "code": "PRICE_CHANGED",
  "timestampUtc": "2026-09-24T08:15:00.000Z",
  "traceId": "00-abcdef1234567890-abcdef1234567890-01"
}
```
The actual API returns the standard envelope without an `activePrice` extension. The frontend retains the rejected quote and amount, then reads `/api/v1/customer/gold-price` for current authoritative data. It shows previous/current prices, updated eight-decimal estimate and “No purchase was made.” Refresh failure retains the old quote and blocks purchase. Explicit “Review new price” enters confirmation; only final confirmation posts the new version with a new idempotency key. An unchanged transport retry retains the original key and payload. No automatic financial retry occurs.

## Session 9 financial reads

Holdings, history and receipt GETs require `AuthPolicies.VerifiedCustomer`: anonymous → 401 `AUTHENTICATION_REQUIRED`; unverified CUSTOMER → 403 `EMAIL_NOT_VERIFIED`; ADMIN without CUSTOMER → 403 `FORBIDDEN`. Invalid/unparseable `page` or `pageSize` → 400 `VALIDATION_ERROR`. An unknown or foreign-owned receipt → identical 404 `RESOURCE_NOT_FOUND` / "Transaction not found.". Missing or stale prices do not fail holdings: quantity is retained and valuation is null per [API_CONTRACT.md](API_CONTRACT.md#48-get-apiv1customerholdings). No new error code or transaction status is introduced.

Session 10: `503 HOLDING_UNAVAILABLE` means a required persisted GoldHolding is missing; goal progress is unavailable, never a fabricated zero. Goal target/date validation uses `400 VALIDATION_ERROR`.

## Session 11 admin errors

All admin endpoints enforce the existing ADMIN policy: anonymous 401 `AUTHENTICATION_REQUIRED`, CUSTOMER 403 `FORBIDDEN`. Invalid pagination, UUID/type filters, publication scale/range/reason or unsupported request fields return 400 `VALIDATION_ERROR`; missing customer/transaction/transaction ledger returns 404 `RESOURCE_NOT_FOUND`. Publication requires CSRF (400 `CSRF_VALIDATION_FAILED`) and safe unexpected errors remain 500 `INTERNAL_ERROR`, including atomic audit insert failure. No new error codes are introduced. Missing price is null on admin dashboard/history; customer quote/purchase continues `PRICE_UNAVAILABLE`. Admin publication connects to the unchanged customer `PRICE_CHANGED` / reconfirmation behavior.
